# Squire Agent Surface (MCP)

## What this is

How external AI agents read, edit, and manage documents: the MCP server and its sixteen tools, the sandboxed modify pipeline, the two credential systems (OAuth delegations and `sk_sqd_` API tokens), the REST export API, and the attribution model that makes agent edits first-class, provenance-tracked collaboration — Squire’s core differentiator.

## Transport and tools

An Express router at `/mcp` speaks JSON-RPC (streamable HTTP); `mcp-stdio-bridge.js` is a thin stdio proxy for CLI clients. Sixteen tools (`server/mcp/tools/`): document CRUD and sharing (list/create/share/set_title), reading (read_document, get_collaborators, get_tool_documentation), editing (modify, undo, redo), version history (list/read/name/restore/compare versions), and create_access_token. Each declares a required scope — `documents:read` or `documents:write` — enforced by the registry, with per-document access re-checked inside every tool. Long tool documentation is served via `get_tool_documentation` because MCP clients truncate descriptions around 2 KB.

## Agents are collaborators, not a backdoor

Tools that touch a document open a real y-websocket presence session on the user’s behalf (`server/mcp/agent-presence.js`): the agent appears as a live cursor named “AgentName (UserName)” with `isAgent: true`, its reads animate highlights, and its edits flow through the same update path as human edits — attributed per-update via `agent_name` and surfaced in version history’s recentAuthors. There is no privileged write path.

**Amendment (Sam, 2026-07-18) — undo/redo become log-derived and stateless: **the undo and redo tools (and the chat Undo/Redo button, which shares their handler) no longer pop a presence session’s in-memory Y.UndoManager. They derive a surgical inverse from the edit’s persisted clock range in the update log, so they work from any server instance and survive session expiry and restarts; the session UndoManager is retired. Mechanism and semantics are designed in Squire Collaboration Core → Version history (amendment of the same date).

## The modify pipeline

- **Sandbox: **scripts run in an isolated-vm V8 isolate (128 MB, 5s default / 30s max timeout) inside a worker thread — two layers of heap isolation, no Node APIs (`server/mcp/sandbox/executor.js`). Helpers (xpath, appendBlocks, cloneBlocks, createFormattedText…) are injected globals.
- **Conflict guard: **the chat layer injects the agent’s last-observed clock; if a different author has advanced the doc since, modify reconstructs the baseline, replays the agent’s own updates, and only reports a conflict (editedBy, no edit applied) on real content divergence.
- **Cross-doc sources: **up to 10 read-only sourceDocGuids (8 MB total) exposed as a sources global; cloneBlocks copies content and the image reconciler re-hosts cross-doc images (or strips inaccessible ones) after the script runs.
- **Output: **a markdown line diff (capped) for the chat transcript, operation summary, the new clock, and server-side mermaid/SVG validation errors (diagrams only render client-side, so the server validates in a jsdom worker).

## Credentials

- **OAuth 2.0 for interactive agents: **authorization-code + PKCE with dynamic client registration; consent creates a delegation; access JWTs live 1 hour with 30-day rotating refresh tokens, signed by a dedicated MCP secret. Revoking a delegation cascades to everything it minted.
- **sk_sqd_ API tokens for shell/REST: **SHA-256-hashed at rest, max 250 active per user, scoped, expiring. `create_access_token` lets an agent mint a short-lived token (≤24 h, scopes capped at its own, no chaining, 50-per-minter cap) so bulk export never passes content through model context.
- **Credential handling — secrets follow the channel rule (Sam, 2026-07-15): **a token is bytes outside the model: it moves Settings → disk → Authorization header, never through the conversation or agent output. Users save tokens to a 0600 file (canonical `~/.squire/token`) instead of pasting them into chat; agents reference the file (`$(cat ~/.squire/token)`) and never print, echo, or retype the raw value — argv also leaks into shell history and process lists. Even self-minted tokens stay out of context: create_access_token returns a one-shot claim URL and the bytes land on disk directly (next bullet); inline: true is the explicit shell-less opt-in. agents.md carries this guidance as part of its front-door contract.
- **create_access_token delivers by one-shot claim, not in-band (Sam, 2026-07-15): **the mint result contains no token. It returns a claim recipe instead: GET /api/tokens/claim, authenticated by a high-entropy one-shot claim code (header only, never in the URL; hashed at rest in Redis; 5-minute TTL). The token itself is minted at claim time and returned as bytes written straight to disk via the returned claim command, so the credential never transits model context. The claim code in the transcript is acceptable residue: one-shot, short-TTL, dead after claim (the 008 lesson retained). An unclaimed mint expires having created nothing; the claim re-checks delegation liveness, the per-minter cap, and the user token cap at mint time (refusals return a reasoned 409 — the claimer already proved possession). inline: true remains the explicit opt-in for shell-less agents, prefixed with a do-not-echo warning. No per-IP limiter on the claim endpoint: a 256-bit one-shot code inside a 5-minute window is not guessable, and the rolled-back login rate-limit machinery stays retired.

## Agent onboarding and discovery

The onboarding story: a user with a Squire account tells their agentic tool to read `https://squiredocs.com/agents.md`. The agent connects to `/mcp` and the standard OAuth discovery chain takes over — browser consent from the user’s logged-in account, no manual token copying in the happy path.

- **agents.md is the agent-facing front door: **served at `/agents.md` as a static asset. It must contain: the MCP endpoint, exact connect one-liners (e.g. `claude mcp add --transport http squire https://squiredocs.com/mcp`), the in-session connect caveat and OAuth walkthrough guidance (next bullets), both credential options, the token-handling guidance (file-based via ~/.squire/token, never pasted into the conversation), tool orientation (the `get_tool_documentation` imperative), and the REST export/import recipe. This doc owns agents.md’s contract — drift between agents.md and the implemented surface is a bug.
- **In-session connect caveat (Sam, 2026-07-14): **MCP clients load server config at startup only — a connect command run from an agent’s own shell inside a live session is invisible to that session (and may land in a config file the client never reads). Observed onboarding failure 2026-07-14: an agent ran the one-liner via its Bash tool, and the user’s `/mcp` showed no servers configured. agents.md must therefore instruct an agent already running inside a session to NOT run the connect command itself, and instead give its user these exact steps: (1) run `claude mcp add --transport http squire https://squiredocs.com/mcp` in a separate terminal; (2) verify with `claude mcp list`; (3) restart the session with the conversation preserved — exit, then `claude --continue` (or `claude --resume` to pick a session); (4) run `/mcp` to confirm the squire server is listed and complete the OAuth consent. — Amended (Sam, 2026-07-15; live-tested with a fresh agent): the DEFAULT suggestion is now a single command the user runs after exiting the session: `claude mcp add --transport http squire https://squiredocs.com/mcp && claude mcp login squire && claude --continue` — it registers the server, completes the browser OAuth login from the terminal, and resumes the conversation in one line (claude --resume to pick a session instead). The four-step choreography above is demoted to troubleshooting fallback: claude mcp list verifies registration, /mcp inside the restarted session confirms and finishes login.
- **OAuth walkthrough guidance (Sam, 2026-07-14): **observed friction 2026-07-14: an agent printed the authorization URL inside a numbered-list item (it wrapped across terminal lines and was hard to copy) and mentioned the paste-back step only in passing, so the user didn’t know to return the callback URL. agents.md must instruct agents that when they hand a user a browser OAuth flow they must: (1) print the authorization URL bare on its own line — never inside list markup, quotes, or trailing punctuation — so one click or one selection copies it; (2) before the user opens it, say what happens after approval: the browser lands on a `localhost` callback page which may show a connection error when the agent runs on a remote machine or container, and that this is expected — the approval still succeeded; (3) state explicitly that the user should copy the FULL URL from the browser’s address bar (`http://localhost:…/callback?code=…`) and paste it back as their next message, and that nothing else is needed.
- **Decision — authorize-link shortener rolled back (Sam, 2026-07-14): **built, deployed, and removed the same day. `POST /mcp/auth/shorten` + `GET /mcp/auth/a/:code` shortened same-origin authorize URLs to defeat terminal line-wrapping, but the shorten step depended on the connecting agent following agents.md guidance mid-flow and never fired in live tests — while the long URL proved clickable end-to-end in the user’s actual terminal. Removed to keep the auth surface minimal. If remote-terminal onboarding friction recurs, revisit device-flow-style pairing (short URL + user code; see the PKCE-only decision below) rather than reviving the shortener.
- **Discovery chain (standards, in order): **unauthenticated `POST /mcp` → 401 with `WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource/mcp"` → RFC 9728 protected-resource metadata → RFC 8414 authorization-server metadata → RFC 7591 dynamic client registration → authorization-code + PKCE (S256 only) → consent page → token. MCP-native clients complete this with zero manual configuration.
- **Consent login round-trip guarantee: **an unauthenticated user landing on the consent page completes Google login and returns to the consent page with all OAuth parameters intact. The `returnTo` path is constrained to same-origin relative paths (open-redirect defense), carried in a short-lived cookie through the Google redirect, and takes precedence over signup/onboarding redirects.
- **Decision — PKCE only, no device flow (Sam, 2026-07-13; superseded in part, Sam, 2026-07-14): **every target client either drives a localhost-redirect PKCE flow natively or can use an API token; RFC 8628 device flow would add a second consent surface and a polling endpoint for no covered client. Revisit only if a covered client appears that can do neither. — The revisit clause was met: sandboxed in-session agents complete PKCE only via the failed-localhost-callback paste-back ritual (the walkthrough guidance above exists to coach exactly that), and the API-token fallback moves a long-lived secret through chat transcripts. Transport-level auth stays PKCE-only (no RFC 8628 at the token endpoint); an app-level onboarding path is added instead — see "MCP-native onboarding: the login tool" below. — Superseded again (Sam, 2026-07-15): the app-level login path (features 008/009) was rolled back the same day it merged; transport-level PKCE OAuth and sk_sqd_ API tokens are once more the only auth paths. See the rollback record below.
- **API-token fallback: **clients that can’t complete browser OAuth use an `sk_sqd_` token from Settings → AI Agent Access as a bearer header. Semantics unchanged from Credentials above.
- **Accepted gap: **the token endpoint accepts and ignores the RFC 8707 `resource` parameter (spec-permitted); revisit if a client is found to require it echoed.

## MCP-native onboarding login (features 008/009) — rolled back

**Decision — device-login bootstrap rolled back; agent auth is standard OAuth only (Sam, 2026-07-15): **features 008 (anonymous login/login_status MCP tools + /activate pairing page) and 009 (the first-class REST login API and choose-your-channel agents.md) were built and merged, then rolled back the same day. The flow was never functional in production: the 008 image reached prod without its migration, so the anonymous login tool errored on the missing table. The rollback deploy removes the anonymous login surface entirely and restores the byte-identical 401 + discovery chain. Live use showed the custom device-style flow did not work well for agents in practice even though they could follow its instructions. Rather than iterate further on a bespoke auth surface, agent credentials return to standard best-practice OAuth.

- **Removed: **the anonymous login/login_status tools (an unauthenticated MCP session sees no tools again), `POST /api/login/start`, `GET /api/login/status`, `GET /api/login/claim` and the `/api/mcp/login/claim` alias, the /activate page, the `mcp_pending_authorizations` table (migration reverted; it never ran in production), the login rate limiter, and the nextSteps block. Tool count in "Transport and tools" is sixteen again.
- **Still in force: **the spec-compliant discovery chain (401 + WWW-Authenticate → RFC 9728 → RFC 8414 → RFC 7591 → PKCE → consent) as the primary onboarding path, and `sk_sqd_` API tokens (Settings → AI Agent Access) as the fallback. agents.md reverts to its pre-008 contract (connect one-liners, in-session connect caveat, OAuth walkthrough guidance, both credential options, REST recipes). The body-parser 400/413 error mapping found in the 009 review was kept — it is independent of login.
- **History: **the full design of the rolled-back flow lives in this document’s version history and in `specs/008-mcp-login-bootstrap/` and `specs/009-rest-login-api/` (whose promotion notes record the rollback). If sandboxed-agent onboarding friction recurs, revisit with fresh evidence rather than reviving this design wholesale — the 2026-07-15 lesson is that agents route around bespoke auth flows toward the standard ones their tooling already knows.

## REST export API

`GET /api/docs/:docId/export?format=markdown` serializes the persisted doc (works with no client connected); view access suffices; browser sessions and API tokens both accepted. Incremental sync pairs it with list_documents’ `updatedSince` + per-doc `clock`. This is the surface design/sync.mjs rides on; the write half is designed in [Proposal: Markdown Import & Two-Way Repo Sync](https://squiredocs.com/d/b6edb804-cf72-416d-9c97-063a23e669c0).

**Amendment (2026-07-14, agent feedback): **the channel rule is now stated across the surface — content that already exists as bytes outside the model travels the byte channel (REST import/export); model context only carries content the model itself creates or transforms. The full REST reference (export AND import/sync) in `get_tool_documentation` is exposed as `rest_api` with `export_api` kept as an alias; create_document/modify descriptions redirect file-holding agents to it; create_access_token shows an import curl example beside the export one; import responses return a canonical-markdown receipt and accept frontmatter=true (born-syncable — see [Proposal: Markdown Import & Two-Way Repo Sync](https://squiredocs.com/d/b6edb804-cf72-416d-9c97-063a23e669c0) §1.2.1).
