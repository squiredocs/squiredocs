# Contract — Collector → monitoring-node export path

**Within 013.** The single egress seam from the prod cluster to the monitoring node.

## The contract

| Property | Value | Source |
|---|---|---|
| Exporter | single `otlp` (gRPC) | RD-4 |
| Target | `<node internal name>:5081` | RD-4, RD-5/RD-13 |
| Target addressing | internal DNS SAN `o11y.squiredocs.internal` + private-IP SAN; no public path | RD-5/RD-13, FR-009 |
| TLS | `tls: { ca_file: /etc/otel/ca/ca.crt }` — trusts the private CA | FR-007, FR-019 |
| CA trust source | `k8s/o11y/ca-trust-configmap.yaml` (public CA cert, plaintext), mounted at `/etc/otel/ca` | FR-007 |
| Delivery semantics | `retry_on_failure` on + bounded persistent `sending_queue` (file_storage) | FR-019 |
| Failure behavior | node down ⇒ buffer then **drop**; **never** app backpressure | FR-019, Edge Case |
| Ports on the node | 5081 gRPC (exporter target); 5080 HTTP+UI stays open for operator/fallback | RD-4 |

## Invariants review asserts

- Exactly one exporter; it is `otlp`/gRPC over TLS to the node — **no** plaintext
  export off-cluster, **no** vendor-specific exporter (OTLP-everywhere keeps the
  backend swappable).
- The `ca_file` path resolves to the mounted CA-trust ConfigMap; the server cert's
  SANs (ops-generated) cover the exporter's target name/IP (FR-009).
- The exporter's queue is bounded so monitoring-node unavailability cannot stall or
  backpressure any prod workload (FR-019).

## Ops-track dependency (post-apply)

The private CA + server cert are generated by the ops track (documented commands,
FR-029); the CA cert is placed into `ca-trust-configmap.yaml` and the server cert/key
laid onto the node via cloud-init. Until then the exporter references a
placeholder/committed CA cert path — real trust is established at apply.


**AMENDED 2026-07-16 (rollout, RD-4):** exporter is `otlphttp` to `https://o11y.squiredocs.internal:5080/api/default` (TLS, private CA, basicauth) — not gRPC 5081. See clarifications-needed.md RD-4 amendment.
