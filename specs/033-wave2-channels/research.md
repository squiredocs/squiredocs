# Phase 0 Research — Wave 2 Distribution Channels

**Feature**: 033-wave2-channels | **Date**: 2026-07-23

All "unknowns" here are design decisions, not open questions: the spec's 9 clarifications are
RATIFIED-BY-DEFAULT and the two format-research files are the buildable ground truth. This
document records the technical decisions the plan rests on — each as Decision / Rationale /
Alternatives — plus the security no-regression analysis (Constitution V, the highest-risk area).

## R1 — Version-carrier generalization (FR-017, spec Gap #2)

**Decision**: Give each channel descriptor a `readVersion(files) → string` function that extracts
the channel's version from its own generated file map. Provide a small helper
`versionFromJson(rel)` that returns `files => JSON.parse(files[rel]).version` for the JSON-manifest
channels (claude-plugin → `.claude-plugin/plugin.json`; cursor-plugin → `.cursor-plugin/plugin.json`;
mcp-registry → `server.json`), and a `versionFromFrontmatter(rel, key='version')` for Kiro
(POWER.md YAML frontmatter `version:`). `diffAgainstMirror` calls `channel.readVersion(fresh)` and
`channel.readVersion(mirrorFilesReadFromDisk)` — the SAME function on both sides — replacing the
current `channel.id === 'mcp-registry' ? 'server.json' : '.claude-plugin/plugin.json'` branch.

**Guard semantics preserved exactly** (this is the security-load-bearing part):
- **Fresh version** comes from `readVersion(fresh)` (in-memory generated bytes) — unchanged.
- **Mirror version** is read by materializing the mirror's version-carrier file(s) from disk into a
  `{rel: content}` map and calling the same `readVersion`. If the carrier file is absent on the
  mirror → genuine first publish (mirrorVersion = null, allowed). If present but `readVersion`
  throws or yields null/non-string → `mirrorVersionUnreadable = true` → **refuse** (never silently
  treated as first publish — 032 review LOW #5, preserved).
- The three refusals downstream are unchanged: `changed && mirrorVersion === freshVersion` → refuse
  (content-change-without-bump); `changed && !semverGt(fresh, mirror)` → refuse (non-forward);
  `mirrorVersionUnreadable` → refuse.
- The refusal message names the channel's version-carrier (e.g. `POWER.md` for Kiro,
  `.cursor-plugin/plugin.json` for Cursor) so the operator knows exactly what to bump — the
  descriptor exposes a human label (`versionCarrierRel` or the message derives it from `readVersion`).

**Rationale**: Kiro has no JSON manifest, so the hardcoded `versionRel` cannot express its carrier.
A per-descriptor `readVersion` is the minimal generalization, is strictly simpler than a growing
`id ===` ladder, and keeps the guard's comparison symmetric (same extractor both sides) so no
channel can accidentally compare a frontmatter version against a JSON version. The guard does NOT
get weaker: every existing refusal still fires, now driven by the descriptor instead of a branch.

**Alternatives considered**:
- *Keep `versionRel` as a plain string on the descriptor and always `JSON.parse`.* Rejected: Kiro's
  carrier is YAML frontmatter in a `.md` file, not JSON — a string+JSON.parse cannot read it.
- *A bundle-root `VERSION` file for ALL channels.* Rejected: changes wave-1 bytes (would add a
  VERSION file to claude-plugin/mcp-registry), violating "must not change wave-1 output".
- *`VERSION` file for Kiro from the start.* Deferred to fallback (RBD-2): frontmatter `version:` is
  the least-invasive carrier; the descriptor's `readVersion` makes switching to a `VERSION` file a
  one-line change if a real Kiro import rejects the unknown frontmatter key (spec Edge Case).

## R2 — Kiro version carrier: POWER.md frontmatter `version:` (RBD-2)

**Decision**: Carry the Kiro version as a `version: "1.0.0"` key in POWER.md's YAML frontmatter,
read by `versionFromFrontmatter('POWER.md')`. Fallback (if a real Kiro import rejects unknown
frontmatter keys, discovered at Sam's submission walk): a bundle-root `VERSION` file, switched by
changing the descriptor's `readVersion` + adding the file to the `files()` map.

**Rationale**: Kiro documents no version field and the power has no manifest, but the publish guard
needs a machine-readable in-bundle version. Frontmatter is the least-invasive carrier and is already
where `name`/`displayName`/etc. live. The frontmatter regex the drift test uses
(`^---\n([\s\S]*?)\n---\n`) reads it without a YAML library.

**Alternatives**: `VERSION` file first (rejected as more files than needed now; kept as the
documented fallback). A separate `version.json` (rejected: an extra non-Kiro artifact in the bundle).

## R3 — Cursor manifest schema vendoring + structural validator (FR-020/021)

**Decision**: Vendor the upstream schema verbatim into
`distribution/schemas/cursor-plugin.schema.json` (distinct filename from the hand-authored Claude
`plugin.schema.json` — FR-020 forbids collision) from
`https://raw.githubusercontent.com/cursor/plugins/main/schemas/plugin.schema.json`, and add a
SOURCES.md entry (upstream URL, retrieval date 2026-07-23, usage, additionalProperties:false note).
Add a hand-rolled `validateCursorPlugin(obj)` structural validator covering: `name` required +
kebab `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`; `version` semver; `author` object with required string
`name` + optional `email`; `license` present as string; `homepage`/`repository` strings when
present; and **rejection of any top-level property not in the schema** (mirroring the upstream
`additionalProperties: false`) — the allowed-keys set is derived from the vendored schema's
`properties` so it tracks the vendored file.

**Rationale**: ajv is still absent (re-confirmed — the 032 constraint stands), so validation stays
the self-contained structural pattern wave 1 established. The Cursor schema's real differentiator vs
the Claude one is the kebab name pattern (allows `.` and `-` internally) and `additionalProperties:
false` — both must be enforced or the manifest could pass locally and fail Cursor's review.

**Alternatives**: Add ajv (rejected: new production dependency solely for a gate — barred by wave 1's
decision + constitution's third-party-dependency justification rule). Reuse the Claude `validatePlugin`
(rejected: different name pattern and no additionalProperties enforcement — would mis-validate).

## R4 — Kiro structural validation (FR-022) — no published schema

**Decision**: Kiro publishes no manifest schema, so add `validateKiroPower(files)` structural checks
run over the generated file map: POWER.md frontmatter parses and carries `name`, `displayName`,
`description`, `keywords` (an array), `author`, `version` (semver); the FR-003 body sections are
present in order (Overview → When to Use This Power → Onboarding → Available Steering Files → When to
Load Steering Files → Available MCP Servers → MCP Configuration → License and Support), with the
License and Support section carrying the license id, the `https://squiredocs.com/privacy` link, and a
support contact; `mcp.json` parses to one `mcpServers.squire-docs` entry with `type:"http"`,
`url` an https URL, and **no `oauth`/`oauthScopes` keys**. Failures exit non-zero naming file +
problem, like every existing validator.

**Rationale**: The submission eligibility set (license + privacy + support) and the DCR posture (no
oauth block) are exactly the things a hand-edit or a generator bug could silently break; structural
checks are the only offline gate available for a schema-less format.

**Alternatives**: Validate only mcp.json (rejected: POWER.md is the required artifact and carries the
eligibility fields). A full markdown-section parser (rejected as over-built: section-heading presence
+ frontmatter-field presence is what eligibility needs, checked by heading-line matching).

## R5 — Cursor `.mdc` rule + `SKILL.md` validation (FR-023)

**Decision**: `validateMdcRule(content)`: frontmatter parses, `description` a non-empty string,
`alwaysApply` exactly `false` (Agent-Requested). `SKILL.md` reuses the shared skill's already-valid
frontmatter (FR-013) — a lightweight check that frontmatter is present. Both structural, offline.

**Rationale**: An Agent-Requested rule with `alwaysApply:true` or an empty `description` would change
its activation semantics silently; pinning both is cheap and matches the research's cited `.mdc`
frontmatter contract.

## R6 — Add-to-Cursor deeplink helper (FR-019/025)

**Decision**: Export `cursorDeeplink({ name = CURSOR_SERVER_KEY, endpoint = PROD_ENDPOINT } = {})`
returning `cursor://anysphere.cursor-deeplink/mcp/install?name=${name}&config=${b64}` where
`b64 = Buffer.from(JSON.stringify({ url: endpoint })).toString('base64')`. The inner object is
exactly `{ "url": PROD_ENDPOINT }` (JSON.stringify key order is deterministic). For the prod endpoint
this yields `config=eyJ1cmwiOiJodHRwczovL3NxdWlyZWRvY3MuY29tL21jcCJ9` (matches the research file's
cited base64). The helper is PURE, derived from `PROD_ENDPOINT` (never a second hardcoded URL), and
its output is embedded byte-identically on the landing page + documentation.

**Rationale**: The deeplink is the one scriptable Cursor on-ramp and must be single-sourced so the
site and the test cannot drift (the wave-1 cross-surface-string rule extended to the deeplink). A
round-trip test base64-decodes the `config` param back to `{url: PROD_ENDPOINT}` and asserts the
`name` param equals the Cursor server key.

**Alternatives**: Hardcode the base64 on the site (rejected: two sources of truth, drift risk — the
exact failure the cross-surface rule prevents). URL-encode the config param (considered: base64 is
already URL-safe for this payload — no `+`/`/` in `eyJ1cmwi...J9`; the helper emits the raw base64 to
match the research + Cursor's documented format, and the test asserts the exact string).

## R7 — Steering file split (RBD-7, FR-005/006/007)

**Decision**: Two steering files: `steering/specs-sync-workflow.md` (the standing loop, the byte
channel, `sk_sqd_` token handling, and the Kiro-native onboarding-as-prose — find the spec in
`.kiro/specs/**` first, sync byte-faithfully via the returned recipe, deliver the doc URL, teach the
loop) and `steering/working-with-squire-docs.md` (what the doc is: two-way sync, attribution,
revertibility, the hero framing that the `.kiro/specs` files these users already write become a
shared/attributed/synced Squire Docs document). POWER.md's "When to Load Steering Files" maps
situations → files (e.g. "When syncing or updating a spec → steering/specs-sync-workflow.md";
"When explaining what Squire Docs adds → steering/working-with-squire-docs.md").

**Rationale**: The split mirrors the observed zapier-power mechanism (POWER.md mapping, FR-007) and
separates the *do* (sync workflow) from the *why* (what the doc is), which is how a situation→file
map wants to branch. Claude-Code-specific mechanics (`/mcp` picker, `/squire:onboard`, plugin-restart)
are omitted (FR-006); Kiro's own connect behavior (automatic browser OAuth on first tool use,
mcp.json hot-reload) is described instead.

**Alternatives**: One combined steering file (rejected: the situation→file map wants at least two
targets to be meaningful; also harder to reframe do-vs-why in one file). Three+ files (rejected as
over-split for the content volume — YAGNI).

## R8 — Security posture: NO REGRESSION as channel count doubles (Constitution V)

The 032 adversarial-review HIGH/MEDIUM/LOW fixes are invariants this feature inherits for the two new
channels for free — **because they are enforced over `CHANNELS`, not per-channel** — and the plan
verifies each still holds:

| Invariant (032 origin) | How it covers wave 2 | Test that proves it |
|---|---|---|
| Dry-run default, zero side effects | CLI unchanged; `generateAll`+`validateBundles` over all 4 | existing dry-run + new channels regenerate |
| `--publish` fail-closed, names all env vars | refusal message joins `CHANNELS.map(mirrorEnv)` — already dynamic; now lists 4 | publish-mechanism no-env test (asserts refusal) |
| Push path prod-pinned, no endpoint param | `diffAgainstMirror`/`publishMirrors` take no endpoint; unchanged | CLI `--publish`+`--endpoint` refusal test |
| No committed default remotes | `mirrorRemoteFor` reads env only; new descriptors add env-only remotes | `mirrorRemoteFor` null-for-all test (loops CHANNELS) |
| Prune-before-stage | `publishMirrors` prunes any mirror working tree; channel-agnostic | first-publish fixture test |
| Drift = committed-bytes vs in-memory + extra-file guard | drift test generalized over CHANNELS; each bundle walked | new-channel byte-match + extra-file assertions |
| Tests strip real `SQUIRE_MIRROR_*`, assert configured==fixture-count | `fixtureEnv` + `configuredCount` reused for new-channel fixtures | new Kiro/Cursor fixture test asserts count |
| Version guard (no-bump refusal, non-forward, unreadable) | generalized via `readVersion`, semantics identical | new-channel content-change-without-bump refusal test |

**The one new risk (FR-017)**: the version-carrier generalization. Mitigation: `readVersion` is the
same function on fresh and mirror; a present-but-unreadable mirror carrier refuses (not first-publish);
the extended publish-mechanism test proves a content-change-without-bump refusal for Kiro (the
frontmatter carrier, the novel path). Any regression here is a Constitution-V HIGH at analyze time.

**Deeplink is not a secret**: it carries only the public prod endpoint; no token, no credential. It is
prod-pinned by construction (derived from `PROD_ENDPOINT`), so it cannot ship a dev URL.

## R9 — No migration, no runtime change (confirm)

**Decision**: Confirmed — this feature touches only `distribution/`, `test/first-run/`, and two
static/built content surfaces. No `server/`, no `shared/` schema, no DB, no node-pg-migrate migration,
no `ai-providers.js`. The `mcp.json` bundles describe the *already-live* prod MCP endpoint; nothing
about the server changes.
