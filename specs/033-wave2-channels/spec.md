# Feature Specification: Wave 2 Distribution Channels — Kiro Power + Cursor Plugin

**Feature Branch**: `033-wave2-channels`

**Created**: 2026-07-23

**Status**: Draft

**Input**: User description: "Wave 2 distribution channels: Kiro Power + Cursor plugin bundles for feature 033-wave2-channels"

**Design source**: `design/plugin-marketplace-publishing.md` — channels §3 (Kiro Powers) and §4 (Cursor Marketplace), the "One server, many storefronts" principles, the Repo layout, "Website and docs surface", and "Publish and release process". Format ground truth: `specs/033-wave2-channels/research-inputs/kiro-power-format.md` and `cursor-plugin-format.md` (researched + cited 2026-07-22; the Cursor manifest schema was re-verified against `https://raw.githubusercontent.com/cursor/plugins/main/schemas/plugin.schema.json` on 2026-07-23 and matches the research file). This feature extends the wave-1 machinery of `specs/032-packaging-distribution` — same generator, same drift guard, same security posture — by adding two channel descriptors, two bundles, one vendored schema, and two site surfaces. It publishes **nothing**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The Kiro Power bundle exists and is generated (Priority: P1)

A Kiro user — pre-qualified spec-driven ICP already generating `.kiro/specs/**` files — imports the Squire Docs power from its public GitHub mirror. Kiro reads `POWER.md`, registers the remote MCP server from `mcp.json`, runs browser OAuth automatically on first use (DCR — no client IDs), and loads the power's steering guidance when the user works with specs. The hero move the steering teaches: the `.kiro/specs` files this user already writes become a shared, attributed, two-way-synced Squire Docs document.

In this repo, `distribution/kiro-power/` is that bundle — every file generated by `distribution/publish.mjs` from `distribution/shared/` plus channel-specific derivations, never hand-edited.

**Why this priority**: The bundle is the deliverable; without it there is nothing to validate, drift-guard, or hand to Sam for submission. Kiro leads the wave because its users are the beachhead ICP.

**Independent Test**: Run `node distribution/publish.mjs` (dry-run default); confirm `distribution/kiro-power/` contains `POWER.md`, `mcp.json`, and `steering/*.md` matching the format research: frontmatter fields present, required body sections present in order (including License and Support), `mcp.json` a remote streamable-HTTP entry pinned to `https://squiredocs.com/mcp` with no `oauth` block.

**Acceptance Scenarios**:

1. **Given** a clean checkout, **When** `node distribution/publish.mjs` runs, **Then** `distribution/kiro-power/` is regenerated byte-identically to the committed tree and validation reports green for the channel.
2. **Given** the generated `POWER.md`, **When** its frontmatter is parsed, **Then** `name`, `displayName`, `description`, `keywords` (an array), and `author` are all present and the body contains the documented sections including a License and Support section carrying a license identifier, the privacy policy link (`https://squiredocs.com/privacy`), and a support contact — the Kiro submission eligibility set.
3. **Given** the generated `mcp.json`, **When** parsed, **Then** it declares one server under `mcpServers` with `type: "http"`, `url: "https://squiredocs.com/mcp"`, and **no** `oauth`/`oauthScopes` block (Squire supports Dynamic Client Registration; a pre-registered clientId is the bug-prone path per the cited Kiro issues).
4. **Given** the steering files, **When** read against `distribution/shared/skill.md` and the Agent Surface contract, **Then** every behavioral claim (two-way sync, attribution, revertibility, byte channel, `sk_sqd_` token file handling) agrees with those sources — reframed Kiro-native, never contradicting them.

### User Story 2 - The Cursor plugin bundle exists and is generated (Priority: P1)

A Cursor user installs the Squire Docs plugin (once listed) or clicks the site's **Add to Cursor** button (available immediately — it installs the MCP server via Cursor's documented deeplink). The plugin bundle carries the manifest, the remote MCP config, the standing spec-loop as an Agent-Requested rule, the Squire skill, and the OSS license Cursor requires.

In this repo, `distribution/cursor-plugin/` is that bundle, generated the same way.

**Why this priority**: Same reasoning as US1 — the second of the two deliverable bundles; the two are independent and either alone is a shippable increment.

**Independent Test**: Run `node distribution/publish.mjs`; confirm `distribution/cursor-plugin/` contains `.cursor-plugin/plugin.json` (valid against the vendored Cursor schema), `mcp.json` (bare `url`, no `type` field — the Cursor remote convention), `rules/squire-spec-loop.mdc`, `skills/squire/SKILL.md`, `LICENSE` (MIT), and `README.md`.

**Acceptance Scenarios**:

1. **Given** the generated `.cursor-plugin/plugin.json`, **When** validated against the vendored `cursor/plugins` schema, **Then** it passes: kebab `name` matching `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`, semver `version`, `author.name`, SPDX `license` of `MIT`, and no properties outside the schema (the upstream schema sets `additionalProperties: false`).
2. **Given** the generated `mcp.json`, **When** parsed, **Then** the server entry is exactly a bare `url` of `https://squiredocs.com/mcp` — **no** `type` field (Cursor infers remote from `url`; this deliberately differs from the Claude/Kiro shape and the drift/validation suite treats it as correct, not drift).
3. **Given** `rules/squire-spec-loop.mdc`, **When** its frontmatter is parsed, **Then** `description` is a non-empty string and `alwaysApply` is `false` (Agent-Requested rule), and its body states the standing loop (sync before a run, read at run start, write status back after) consistently with `shared/skill.md`.
4. **Given** `skills/squire/SKILL.md`, **When** compared to `distribution/shared/skill.md`, **Then** it is the shared content near-verbatim: byte-faithful body plus the standard do-not-hand-edit generated header after the frontmatter.
5. **Given** the bundle, **When** inspected, **Then** `LICENSE` is the same MIT text the wave-1 channels generate (single source of truth for holder + year) — Cursor requires plugins be open source.

### User Story 3 - One command generates, validates, and (for Sam) pushes all four channels (Priority: P2)

The maintainer or CI runs `node distribution/publish.mjs` and gets a dry-run regeneration + validation of **four** channels: `claude-plugin`, `mcp-registry`, `kiro-power`, `cursor-plugin`. Sam, and only Sam, runs `--publish` with mirror env vars set to push the public mirrors. The wave-1 security posture is unchanged: dry-run default, prod-pinned push path, fail-closed on missing/unreachable remotes, version-bump guard, no committed default remotes.

**Why this priority**: The channel registry (RBD-3 in wave 1) was built exactly so wave 2 is "add a descriptor"; this story proves that promise while re-asserting the 032 review HIGHs cannot regress.

**Independent Test**: Dry-run shows 4 channels regenerated + validated. `--publish` with no env vars fails closed listing all four channels' env var names. Bare-repo fixture tests exercise the push + version guard for the new channels.

**Acceptance Scenarios**:

1. **Given** no `SQUIRE_MIRROR_*` env vars, **When** `node distribution/publish.mjs --publish` runs, **Then** it refuses before any side effect and the refusal names `SQUIRE_MIRROR_KIRO_POWER` and `SQUIRE_MIRROR_CURSOR_PLUGIN` alongside the wave-1 vars.
2. **Given** a local bare-repo fixture configured as the kiro-power (or cursor-plugin) mirror, **When** publish runs twice with content changed but the channel version unchanged between runs, **Then** the second run is refused by the version-bump guard, naming the channel's version-bearing file.
3. **Given** any `--publish` invocation combined with `--out` or a non-prod `--endpoint`, **When** the CLI parses arguments, **Then** it refuses with exit 2 exactly as wave 1 does (the prod-pinned publish invariant covers the new channels for free because the push path takes no endpoint parameter).
4. **Given** a change to one channel's content, **When** it ships, **Then** only that channel's version needs bumping — all four channel versions are independent; the two new channels start at `1.0.0`.

### User Story 4 - Drift, schema, and deeplink guards cover the new channels in CI (Priority: P2)

A contributor hand-edits a generated file in `distribution/kiro-power/` or `distribution/cursor-plugin/`, or commits an extra file the generator does not emit, or lets the site's Add-to-Cursor link drift from the prod endpoint — and the always-run test suite fails, naming the file and the fix.

**Why this priority**: The generated-copies rule is what makes "ground truth lives in this repo" true; without the guard, wave-2 bundles rot silently exactly as wave 1's would have.

**Independent Test**: `node --test test/first-run/bundle-drift.test.mjs` passes on a clean tree; a one-byte edit to any generated file in either new bundle fails it naming that file; an extra committed file in either bundle fails it; the deeplink test decodes the computed Add-to-Cursor URL back to the prod server object.

**Acceptance Scenarios**:

1. **Given** the committed tree, **When** the drift test runs, **Then** every file in both new bundles byte-matches a fresh in-memory regeneration (never regenerate-then-compare), each channel's `mcp.json` endpoint field is the only drift-exempt field, and a separate assertion pins each committed endpoint to exactly `https://squiredocs.com/mcp`.
2. **Given** a committed file in either new bundle that the generator does not emit, **When** the drift test runs, **Then** it fails flagging the unexpected file (extra-file guard extended to all four channels).
3. **Given** the exported Add-to-Cursor deeplink helper, **When** its `config` query parameter is base64-decoded, **Then** it parses to exactly the JSON object `{"url": "<PROD_ENDPOINT>"}` and the full link is `cursor://anysphere.cursor-deeplink/mcp/install?name=<server-name>&config=<base64>` — computed from `PROD_ENDPOINT`, never a hardcoded string.
4. **Given** the full deterministic first-run suite (`npm run test:first-run`), **When** it runs after this feature, **Then** every pre-existing wave-1 test still passes unmodified in intent (publish-mechanism, drift, budgets, harness).

### User Story 5 - The site and docs surface both channels honestly (Priority: P3)

A visitor on the landing page or the documentation site sees, in the "works with your coding agent" surface: an **Add to Cursor** button (the deeplink — works today, connects the MCP server) and a **Kiro** section with the public power repo link and the exact import steps (Kiro IDE → Powers panel → Add Custom Power → Import power from GitHub → paste repo URL → Install). There is deliberately **no** "Add to Kiro" button: no embeddable deeplink exists — the registry-page button is Kiro's, not ours — and the copy does not pretend otherwise. All copy is honest-confident voice and says "Squire Docs".

**Why this priority**: Distribution surfaces are what convert; but they depend on the bundles and the deeplink helper existing first, and they can ship in the same release without blocking the bundles.

**Independent Test**: Open `client/public/landing.html` and the built documentation page; verify the Cursor button's `href` equals the computed deeplink byte-for-byte, the Kiro section names the mirror repo URL and the five import steps, and no copy claims marketplace/registry listing that has not happened.

**Acceptance Scenarios**:

1. **Given** the landing page agent block, **When** rendered, **Then** it contains an Add to Cursor control whose link is the exact computed deeplink, plus a one-line honest description of what it does (connects the Squire Docs MCP server in Cursor; the full plugin arrives via the Cursor marketplace once listed).
2. **Given** the Kiro section on either surface, **When** read, **Then** it links `https://github.com/squiredocs/squire-kiro-power` and gives the repo-import steps verbatim — repo link + steps, not a fake button.
3. **Given** `documentation/agents-and-mcp.md`, **When** the documentation build and its validation/terminology gates run, **Then** they pass, and the new Cursor/Kiro install content coexists coherently with the existing manual Kiro `mcp.json` snippet (which stays, for users who want config-file setup without the power).
4. **Given** a repo test over the committed site sources, **When** it runs, **Then** the deeplink string on every surface that carries it is byte-identical to the generator-computed value (cross-surface drift is a defect, same rule as wave 1's install one-liners).

### Edge Cases

- **Mirror repo does not exist yet** (`squiredocs/squire-kiro-power`, `squiredocs/squire-cursor-plugin` are owed Sam ops): publish `--publish` fails closed on clone; dry-run and all tests are unaffected. The site may link the repo ahead of its existence only in the same "advertises ahead of availability by design" sense wave 1 used for agents.md — acceptable, called out in the handoff so Sam creates repos before (or with) the deploy.
- **Kiro frontmatter tolerance**: the version-carrier default (a `version:` field in POWER.md frontmatter) is not a documented Kiro field. If a real Kiro import rejects unknown frontmatter keys, fall back to a `VERSION` file at bundle root (see Assumptions + clarifications ledger); the version guard reads whichever carrier the channel descriptor declares.
- **Cursor schema evolution**: upstream `plugin.schema.json` changes are handled by the existing SOURCES.md refresh procedure (re-fetch, diff, adjust structural validator, bump retrieval date) — no live fetch at validation time, ever.
- **Endpoint override for rehearsals**: `--out`/`--endpoint` materialization applies to the new channels identically (each channel's `mcp.json` endpoint field is the single overridable field); the committed tree and the publish path never carry a non-prod endpoint.
- **A user clicks Add to Cursor without Cursor installed**: the `cursor://` scheme goes nowhere; the surface copy sits next to the documentation link so the fallback path (docs page, manual config) is one click away. No JS scheme-detection is required.
- **Deeplink name collision**: the deeplink installs a server named after the bundle's server key into the user's Cursor config; re-clicking is idempotent-by-overwrite in Cursor's UI flow — no state we manage.
- **Steering drift vs shared/**: steering files are authored derivations (reframed, not byte-copies of shared/), so the drift guard pins them to the **generator's** output — a hand-edit to the committed steering file fails drift; changing steering content legitimately means editing its derivation in `publish.mjs` (and bumping the Kiro channel version).

## Requirements *(mandatory)*

### Functional Requirements

#### Kiro Power bundle (US1)

- **FR-001**: The repository MUST contain `distribution/kiro-power/` as the Kiro Power bundle, fully generated by `distribution/publish.mjs`, with exactly this layout: `POWER.md` at bundle root, `mcp.json`, and one or more `steering/*.md` files. No file in the bundle may be hand-authored in place; every file is emitted by the generator.
- **FR-002**: `POWER.md` MUST carry YAML frontmatter with `name` (kebab-case internal id — changing it later forces user reinstalls, so it is chosen once), `displayName` and `description` in the honest-confident "Squire Docs" voice, `keywords` as an array of trigger words covering the spec-driven domain (e.g. specs, spec-driven, kiro-specs, requirements, design, review, attribution), and `author`.
- **FR-003**: The `POWER.md` body MUST contain, in the research-documented order: Overview → When to Use This Power → Onboarding → Available Steering Files → When to Load Steering Files (a conditional mapping from situations to specific steering files) → Available MCP Servers → MCP Configuration → License and Support. The License and Support section MUST state the bundle's license, link the privacy policy at `https://squiredocs.com/privacy`, and give a support contact — for both the power and the Squire Docs MCP server (Kiro submission eligibility requires all three).
- **FR-004**: The Kiro `mcp.json` MUST declare the Squire Docs server as a remote streamable-HTTP entry: `type: "http"`, `url` pinned to `https://squiredocs.com/mcp`, `disabled: false`, `autoApprove: []`, and MUST NOT contain an `oauth`/`oauthScopes` block — Squire supports Dynamic Client Registration and Kiro self-registers; a pre-registered client id is the documented bug path.
- **FR-005**: The steering content MUST be derived from `distribution/shared/` but reframed Kiro-native: the hero framing is hosting the `.kiro/specs/**` files Kiro users already generate as a shared, attributed, two-way-synced Squire Docs document. It MUST carry the standing loop (sync before a run, read at run start, write status/design back after), the byte-channel rule (never retype file content; `import_markdown_file` recipe / REST export), and the `sk_sqd_` token-handling rules (`~/.squire/token`, 0600, never in the transcript) — each claim agreeing with `distribution/shared/skill.md` and the Agent Surface (MCP) contract.
- **FR-006**: Because Kiro has no command surface, the onboarding flow MUST be folded into steering prose (per the design's "folded into steering prose on channels without commands"): find the spec (`.kiro/specs/**` first), sync it byte-faithfully via the returned recipe, deliver the doc URL, teach the loop. Claude-Code-specific mechanics from `shared/onboard.md` (the `/mcp` picker, `/squire:onboard`, plugin-restart caveats) MUST NOT appear; Kiro's own connect behavior (automatic browser OAuth on first tool use, hot-reload of `mcp.json`) is described instead.
- **FR-007**: Steering-file loading MUST be driven by the POWER.md "When to Load Steering Files" mapping (the power-internal mechanism observed in the real zapier power), not by workspace-steering `inclusion:` frontmatter, whose behavior for power-internal files is undocumented (flagged in research).
- **FR-008**: The Kiro channel MUST carry its own independent version starting at `1.0.0`, machine-readable from inside the bundle so the publish version-bump guard can compare mirror vs fresh (see Assumptions for the carrier default).

#### Cursor plugin bundle (US2)

- **FR-009**: The repository MUST contain `distribution/cursor-plugin/` as the Cursor plugin bundle, fully generated, with exactly this layout: `.cursor-plugin/plugin.json`, `mcp.json` at bundle root (the filename Cursor requires), `rules/squire-spec-loop.mdc`, `skills/squire/SKILL.md`, `LICENSE`, `README.md`. Components are auto-discovered from the default `rules/`, `skills/` directories and `mcp.json`; no glob overrides in the manifest.
- **FR-010**: `.cursor-plugin/plugin.json` MUST validate against the vendored Cursor plugin schema: kebab `name` matching `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`, semver `version` starting at `1.0.0`, `description` and `displayName` saying "Squire Docs" in the honest-confident voice, `author` with a `name`, `license: "MIT"`, `repository` pointing at the public mirror, `homepage: "https://squiredocs.com"`, and no properties outside the schema (upstream sets `additionalProperties: false`).
- **FR-011**: The Cursor `mcp.json` MUST declare the server with a bare `url` of `https://squiredocs.com/mcp` and MUST NOT include a `type` field — Cursor's convention treats a bare `url` as remote; and MUST NOT include an `auth` block (DCR makes it unnecessary). The validation suite MUST assert this Cursor-specific shape (i.e. the absence of `type` is correct here and only here).
- **FR-012**: `rules/squire-spec-loop.mdc` MUST be an Agent-Requested rule: frontmatter `description` set (stating when to apply — working from a spec/design doc, keeping the Squire Docs spec and repo in sync) and `alwaysApply: false`; the body restates the standing loop consistently with `shared/skill.md`, adapted to Cursor (no Claude-plugin command references).
- **FR-013**: `skills/squire/SKILL.md` MUST be generated from `distribution/shared/skill.md` near-verbatim: the shared frontmatter and body byte-faithful, plus the standard do-not-hand-edit generated header inserted after the frontmatter (the same `withGeneratedHeader` transform wave 1 uses).
- **FR-014**: The bundle MUST include the MIT `LICENSE` generated from the same single-source license text as the wave-1 channels (Cursor requires plugins be open source), and a `README.md` describing what the plugin is, what installing it does (MCP + rule + skill), the OAuth/first-use behavior (browser sign-in; Google sign-in creates the account if none exists), and where the ground truth lives (generated from this repo — do not PR the mirror).
- **FR-015**: The feature MUST NOT rewrite `distribution/shared/skill.md` or `distribution/shared/onboard.md` — the M2-signed-off sources are consumed read-only, exactly as in wave 1 (whose FR-006 carries the same rule).

#### Generator and publish machinery (US3)

- **FR-016**: `distribution/publish.mjs` MUST gain two channel descriptors — `kiro-power` and `cursor-plugin` — in the existing `CHANNELS` registry, each with a pure `files()` map, its committed `outDir`, its drift-exempt endpoint field (`mcp.json` in both), its schema/validator bindings, and its mirror env var: `SQUIRE_MIRROR_KIRO_POWER` and `SQUIRE_MIRROR_CURSOR_PLUGIN`. Adding the channels MUST NOT change the generated bytes of the wave-1 channels.
- **FR-017**: Each new channel MUST version independently (own exported version constant, starting `1.0.0`); the publish version-bump guard MUST read each channel's version from a descriptor-declared version-bearing file rather than the current hardcoded two-channel mapping, and MUST behave for the new channels exactly as for wave 1 (refuse content-change-without-bump, refuse non-forward bumps, refuse unreadable mirror versions).
- **FR-018**: The publish path's security posture MUST be unchanged and MUST cover the new channels: dry-run default with zero side effects; `--publish` fail-closed with no configured remotes (message naming all four env vars); push path prod-pinned with no endpoint parameter; `--publish` mutually exclusive with `--out`/non-prod `--endpoint`; no committed default remotes; mirror working-tree pruned before staging. None of the 032 adversarial-review HIGH fixes may regress.
- **FR-019**: `publish.mjs` MUST export a pure Add-to-Cursor deeplink helper that computes `cursor://anysphere.cursor-deeplink/mcp/install?name=<server-name>&config=<base64>` where `<base64>` is the base64 of the JSON-serialized inner server object (`{"url": PROD_ENDPOINT}`) — derived from `PROD_ENDPOINT`, the single endpoint constant, never a second hardcoded URL.

#### Schema vendoring and validation (US4)

- **FR-020**: The Cursor plugin manifest schema MUST be vendored verbatim into `distribution/schemas/` from `https://raw.githubusercontent.com/cursor/plugins/main/schemas/plugin.schema.json` (github.com/cursor/plugins), and `distribution/schemas/SOURCES.md` MUST record its upstream URL, retrieval date, and usage, following the existing refresh procedure. The vendored filename MUST NOT collide with the existing hand-authored Claude `plugin.schema.json`.
- **FR-021**: Validation MUST remain offline, deterministic, and dependency-free (ajv is absent from the tree — the wave-1 constraint stands): a hand-rolled structural validator for the Cursor manifest covering at minimum the `name` pattern, semver `version`, `author` shape (`name` required string, optional `email`), `license` presence as a string, URI-typed `homepage`/`repository` being strings, and rejection of top-level properties not in the schema (mirroring `additionalProperties: false`).
- **FR-022**: Kiro has no published schema; the Kiro channel MUST get structural validation instead: POWER.md frontmatter parses and carries the FR-002 required fields with `keywords` an array; the FR-003 body sections present; `mcp.json` matches the FR-004 shape including the absence of `oauth` keys. Failures exit non-zero naming file and problem, like every existing validator.
- **FR-023**: The Cursor rule and skill files MUST get structural checks: `.mdc` frontmatter parses with a non-empty `description` and `alwaysApply: false`; `SKILL.md` frontmatter present (the Cursor skill format matches the already-valid shared frontmatter).

#### Drift and test coverage (US4)

- **FR-024**: The always-run drift test (`test/first-run/bundle-drift.test.mjs`) MUST cover both new channels with the full wave-1 guard set: byte-match of every committed file against the pure in-memory expected bytes (never regenerate-then-compare); the per-channel `mcp.json` endpoint field as the only exempt field with every other byte asserted; a separate prod-pin assertion per committed endpoint; and the extra-file guard over each bundle directory. The mechanism SHOULD generalize over `CHANNELS` rather than duplicating per-channel walkers.
- **FR-025**: A test MUST assert the deeplink helper round-trips: base64-decoding the `config` parameter of the computed deeplink yields exactly the JSON object whose `url` equals `PROD_ENDPOINT`, and the `name` parameter equals the bundle's server key.
- **FR-026**: The publish-mechanism suite MUST prove the push path for at least one new channel against local bare-repo fixtures only (first publish, version-bump refusal, fail-closed empty env, env-stripping so no real `SQUIRE_MIRROR_*` can ride along), and every existing wave-1 test MUST still pass.

#### Site and documentation surfaces (US5)

- **FR-027**: `client/public/landing.html` (with styles in `client/public/marketing.css`) MUST extend the existing "works with your coding agent" block with: (a) an **Add to Cursor** control linking the exact computed deeplink, with one honest line about what it does; (b) a **Kiro** section linking the public power repo and giving the import steps: Kiro IDE → Powers panel → Add Custom Power → Import power from GitHub → paste the repo URL → Install. There MUST NOT be an "Add to Kiro" button or any implication one exists — no embeddable Kiro deeplink exists; the Add-to-Kiro button is registry-only.
- **FR-028**: `documentation/agents-and-mcp.md` MUST gain matching per-ecosystem install sections for Cursor (deeplink + what it installs + marketplace note) and Kiro (power import steps + repo link), coexisting with the existing manual Kiro `mcp.json` snippet (retained for config-file setup), and the documentation build with its validation and terminology gates MUST pass.
- **FR-029**: The deeplink string MUST be byte-identical everywhere it appears (landing page, documentation), and a repo test MUST assert each committed surface's deeplink equals the generator-computed value — the wave-1 cross-surface-drift rule extended to the deeplink.
- **FR-030**: All user-facing copy MUST say "Squire Docs" (bare `squire`/`squire-docs` only as namespacing/identifiers), stay in the honest-confident voice, and MUST NOT claim a listing that has not happened: the Cursor marketplace listing and the Kiro Powers registry listing are pending Sam submissions, and copy is written to be true both before and after listing (e.g. "install from the repo" phrasing for Kiro, "connects the MCP server" for the Cursor button).

#### Content truth and process (cross-cutting)

- **FR-031**: Every behavioral claim in the newly authored content (POWER.md body, steering files, the `.mdc` rule, the READMEs, the site copy) MUST be true of the product today and MUST agree with `design/agent-surface-mcp.md` and `distribution/shared/` — two-way sync, attribution, revertibility, the byte channel, token handling, OAuth-creates-account. Divergence from the Agent Surface contract is a defect, the same drift rule the design sets for the Claude plugin.
- **FR-032**: The feature MUST NOT perform any publishing: no mirror pushes, no registry or marketplace submissions, no new repos. Sam-only operations MUST be recorded in this spec's handoff checklist and carried into promotion notes at implement time.
- **FR-033**: The feature MUST NOT create wave-3 artifacts (`gemini-extension/`, `codex-plugin/`, aggregator files) and MUST NOT edit `design/*`, `CLAUDE.md`, `README.md`, `docs/dev.md`, or the served `agents.md` (agents.md's contract is owned by the Agent Surface doc and covers agent-facing connect paths; Cursor/Kiro user-facing install lives on the landing/documentation surfaces this feature owns). The design doc's channel-status ledger update is orchestrator work, flagged as owed.
- **FR-034**: The exact marketing/steering prose is authored at implement time within this spec's testable constraints and is a candidate for Sam's later tone review — recorded as a promotion note, never a blocker.

### Key Entities

- **Channel descriptor**: an entry in the generator's `CHANNELS` registry — id, output directory, pure file map, drift-exempt endpoint field, schema/validator bindings, mirror env var, version-bearing file. Wave 2 adds `kiro-power` and `cursor-plugin`.
- **Kiro Power bundle**: `POWER.md` (frontmatter + ordered body sections incl. License and Support) + `mcp.json` (remote HTTP, DCR, no oauth block) + `steering/*.md` (Kiro-native reframing of shared content). Mirrors to `squiredocs/squire-kiro-power`. Version 1.0.0, independent.
- **Cursor plugin bundle**: `.cursor-plugin/plugin.json` (schema-valid manifest) + root `mcp.json` (bare url) + `rules/squire-spec-loop.mdc` (Agent-Requested) + `skills/squire/SKILL.md` (shared, near-verbatim) + `LICENSE` (MIT) + `README.md`. Mirrors to `squiredocs/squire-cursor-plugin`. Version 1.0.0, independent.
- **Vendored Cursor schema**: byte-verbatim copy of the upstream `plugin.schema.json` (draft-07, additionalProperties:false), recorded in SOURCES.md, backing the hand-rolled structural validator.
- **Add-to-Cursor deeplink**: `cursor://anysphere.cursor-deeplink/mcp/install?name=…&config=BASE64({"url": PROD_ENDPOINT})` — computed by an exported helper, asserted by test, embedded byte-identically on the site surfaces.
